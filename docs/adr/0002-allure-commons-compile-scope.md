# ADR 0002: `allure-java-commons` остаётся в scope `compile`

**Статус:** принято
**Дата:** 2026-08-04

## Контекст

Все feature-зависимости библиотеки объявлены `provided`: WireMock, RestAssured, Kafka, Liquibase,
Mockito, spring-jdbc и прочие приходят у потребителя **его** версий, а модуль, чьей библиотеки
нет, тихо выключается.

Из этого правила ровно одно исключение — `io.qameta.allure:allure-java-commons` в scope
`compile`. Это единственная версия, которую мы **навязываем** чужому дереву зависимостей.

У навязывания есть цена. Если у потребителя свой Allure новее нашего:

```
consumer → allure-spring-test → allure-java-commons:2.25.0   (глубина 2)
consumer → allure-junit5:2.35.4 → allure-java-commons:2.35.4 (глубина 2)
```

Глубина одинаковая, значит Maven возьмёт объявленную **раньше** — исход зависит от порядка строк
в чужом pom. Стоим раньше мы — его `allure-junit5` получает commons 2.25 и ломается. Дефект
худшего класса: чужая библиотека падает из-за нашей.

Соблазн очевиден: перевести в `provided` и сделать все зависимости однородными.

## Решение

Оставляем `compile`.

## Почему не `provided`

Наши листенеры регистрируются через `META-INF/spring.factories`, а Spring грузит их
`SpringFactoriesLoader`-ом с `TestContextFailureHandler` — обработчиком, который **молча
пропускает** класс, не сумевший загрузиться.

Значит потребитель без `allure-java-commons` получил бы не громкий `NoClassDefFoundError`, а
**молчаливое отключение всей библиотеки**: тесты зелёные, отчёт пустой, причина не названа.

Это ровно тот класс поломок, против которого построена вся сетка сигналов проекта — канарейки,
гейт сбоев перехвата, инвентарь видов шагов. Менять единственную громкую поломку («нет
зависимости — не собирается») на самую тихую было бы прямым противоречием самим себе.

## Чем компенсируем цену

- **Раздел в README** «Если у вас другая версия Allure»: импорт `allure-bom` в свой
  `dependencyManagement` бьёт любое транзитивное разрешение. Плюс два запасных варианта.
- **Заметка про Gradle**: там highest-wins, конфликта нет вовсе.
- **Гейт `unit/PomCompatibilityTest#singleCompileScopeDependency`**: транзитивно навязываемая
  зависимость обязана остаться ровно одна. Вторая — это уже не «абзац в README», а нерешаемая
  для потребителя тема, поэтому её появление должно быть предметом ревью, а не следствием
  невнимательного `<dependency>` без `<scope>`.
- **Канарейка `canary/AllureApiCanaryTest`**: поверхность API Allure, которой мы пользуемся,
  плюс сверка рантайм-версии с объявленными границами (`compat.allure.min/max` в pom).
  Проверено прогоном: на 2.20.0 и на 2.35.4 полный сьют зелёный.

## Что остаётся непокрытым

Сценарий «скомпилировано против 2.25, выполняется на 2.35» матрицей не проверяется — она
пересобирает проект под каждую версию. Сейчас это закрыто фактом: поверхность API
(`AllureLifecycle`, перегрузки `Allure.step`, модельные классы) байт-идентична с 2.15 по 2.35.4.

Полная симуляция потребителя (`maven-invoker` + `requireUpperBoundDeps`) — кандидат на следующий
заход, если библиотека пойдёт в Central.
