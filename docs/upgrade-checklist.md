# Чек-лист апгрейда: Java 21 → 25, Spring Boot 3.5.8 → 4.1.0

Сетка сигналов построена ДО апгрейда (см. `docs/acceptance-report-standard.md`, «Уровень C»).
Этот файл — порядок действий в самой ветке апгрейда и список того, что заведомо придётся
править руками.

## Правило: одна переменная за раз

Boot 4.1 собран под JDK 17, поэтому оси разделимы. Разделяй — иначе на любое расхождение будет
два подозреваемых, и разбор подорожает вдвое.

| Фаза | Что меняем | Что доказывает |
|---|---|---|
| 1 ✅ | Java 21 → 25, Boot остаётся 3.5.8 | риски JDK: формат классов vs byte-buddy, self-attach (JEP 451), `sun.misc.Unsafe`, работа RestAssured (Groovy) и WireMock, `@EmbeddedKafka` |
| 2 ✅ | Boot 3.5.8 → 4.1.0, Java остаётся 21 | риски Spring: переезд кастомайзеров, Hibernate 7, Liquibase 5, Kafka 4, JUnit 6 |
| 3 | обе оси вместе | взаимодействия (RestAssured 6 + Groovy 5 на JDK 25) |

Каждая фаза заканчивается полным `mvn clean test` — включая второй прогон инвентаря.

## Фаза 1 (Java 25) — ПРОЙДЕНА

`mvn -Pjava25 clean test` на Temurin/Homebrew **25.0.4**, Boot 3.5.8 — всё зелёное:

| Сигнал | Результат |
|---|---|
| канарейка «byte-buddy знает формат классов JVM» | зелёная (bb 1.17.8) |
| `installed=true` (self-attach, JEP 451) | да, 151 трансформация |
| сбои трансформации | 0 (единственная запись — намеренная проба из `InstrumentationDiagnosticsTest`) |
| WARNING «модуль не активирован» | нет ни одного |
| уровни A и B (456 тестов — счёт НА ДАТУ прогона, сьют с тех пор рос) | зелёные |
| инвентарь видов шагов | зелёный, **эталон не сдвинулся ни на строку** |

Инвентарь тут работает как НАСТОЯЩИЙ гейт (в отличие от compat-профилей по версиям библиотек):
версии библиотек те же, а тексты шагов от версии JVM не зависят. Поехал эталон на этой оси —
разбирать, а не обновлять.

Профиль форкает только тесты (`surefire <jvm>`), компиляция остаётся `release=21` — проверяется
ровно то, что получит потребитель: jar под 21 на JVM 25. Maven и плагины остаются на 21, поэтому
при поломке подозреваемый один.

Шум в stderr, который считаем нормой (не наш код):

- `sun.misc.Unsafe::objectFieldOffset has been called by net.bytebuddy…ClassInjector$UsingUnsafe`
  — терминально устаревший метод, byte-buddy 1.17.8 всё ещё им пользуется. Когда JDK запретит
  его окончательно, лечится подъёмом byte-buddy, а не правкой у нас;
- `Sharing is only supported for boot loader classes…` — CDS отключается, потому что агент
  дописывает bootstrap classpath. Ожидаемо для любого java-агента.

## OpenRewrite — РАЗВЕДКА, а не исполнитель (проверено на фазе 2)

```
mvn -U org.openrewrite.maven:rewrite-maven-plugin:run \
  -Drewrite.recipeArtifactCoordinates=org.openrewrite.recipe:rewrite-spring:RELEASE \
  -Drewrite.activeRecipes=org.openrewrite.java.spring.boot4.UpgradeSpringBoot_4_0
```

Раньше здесь было написано «механические переезды делает OpenRewrite, а не человек».
**Это оказалось неверно.** Рецепт прогнали на фазе 2, его диф разобрали построчно и
ОТВЕРГЛИ целиком; правки внесли руками. Что он сделал не так:

- поднял Boot до **4.0.7** (умеет только 4.0.x), а целились в 4.1.0;
- прописал `<version>` шести зависимостям — в проекте версии берутся из BOM;
- в профиле `compat-boot-min` заменил `${compat.boot.min}` на конкретную версию, то есть
  **тихо убил нижнюю границу совместимости**;
- подменил `liquibase-core` (provided) стартером, добавил `spring-boot-starter-restclient`
  в **compile**-scope — навязало бы стартер каждому потребителю;
- поднял версии core-плагинов, зафиксированные осознанно;
- прошёлся миграцией Java 8→17 по 12 файлам `src/main` (`isPresent()`→`isEmpty()`,
  `Paths.get`→`Path.of`) — к апгрейду Boot отношения не имеет, а лишний шум в дифе
  прячет настоящие правки.

**Как пользоваться правильно:** прогнать, ВЫПИСАТЬ из дифа список переездов, `git checkout -- .`,
внести переезды руками. Список переездов он даёт хороший — три из них (ниже) чек-лист
не предвидел. Плагин в сборку НЕ добавляем.

## Фаза 2 (Boot 4.1.0) — ПРОЙДЕНА

`mvn clean test` на Boot 4.1.0 / Java 21: **462 теста зелёные**, включая второй прогон инвентаря.
Сигналы читались сверху вниз, каждый уровень разбирался до перехода к следующему.

| Сигнал | Что показал |
|---|---|
| модель Maven / компиляция | 5 переездов типов, из них **3 чек-лист не предвидел** (таблица ниже) |
| канарейки `InstrumentationApiCanaryTest` | зелёные — `MovedTypeNames` сошлись с реальностью |
| `instrumentation-diagnostics` | `installed=true`, 143 трансформации, сбоев сверх известных нет |
| WARNING «модуль не активирован» | ни одного |
| инвентарь видов шагов | 2 расхождения, оба разобраны и объяснены (ниже) |

**Переезды, которых в чек-листе НЕ БЫЛО** (нашлись компиляцией):

| класс | Boot 3.x | Boot 4.1 |
|---|---|---|
| `AutoConfigureMockMvc` | `…test.autoconfigure.web.servlet` | `…webmvc.test.autoconfigure` |
| `AutoConfigureWebTestClient` | `…test.autoconfigure.web.reactive` | `…webtestclient.autoconfigure` |
| `TestRestTemplate` | `…test.web.client` | `…resttestclient`, **и больше не подаётся сам** — нужна `@AutoConfigureTestRestTemplate` |
| `EntityScan` | `…autoconfigure.domain` | `…persistence.autoconfigure` |
| `RestTemplateBuilder` | `…web.client` | `…restclient` (артефакт `spring-boot-restclient`) |
| `LocalServerPort` | — | остался на месте |

**Автоконфигурация уехала в модули по технологиям.** Голого `spring-kafka`/`liquibase-core`
в test-scope больше не хватает: контекст поднимается, но БЕЗ бинов (`kafkaListenerContainerFactory`,
`SpringLiquibase`). Симптом обманчив — не «класс не найден», а «бина нет». Нужны стартеры
`spring-boot-starter-kafka` / `spring-boot-starter-liquibase`.

**Расхождения инвентаря, оба законные:**
1. пропал вид `Проверка: … — значение <V> не null` — наша осознанная правка (см. ниже про
   кражу тела ответа);
2. у `MockMvcReportIT | HTTP Response` снят маркер формы `¶N`: ответ 404 в Boot 4 приходит
   БЕЗ заголовков, вложение выродилось в одну строку `404`. Что это не наша деградация,
   видно из того же прогона — остальные четыре вложения заголовки печатают.
   ⚠️ Цена: этот вид больше не стережётся маркером формы.

**Главное, что дала фаза 2 — не поломка апгрейда, а настоящий БАГ библиотеки.**
В Spring 7 проверки статуса переехали в общий `AbstractStatusAssertions`, где появилась
внутренняя строка `AssertionErrors.assertNotNull("exchangeResult unexpectedly null", exchangeResult)`.
Наш перехват ассертов рендерил аргумент в имя шага через `toString()`, а
`ExchangeResult.toString()` печатает тело ответа — которое в Spring 7 стало ОДНОРАЗОВЫМ.
Итог: у потребителя падал его собственный `expectBody()`, хотя он всего лишь добавил нашу
зависимость. Починено: в null-проверках значение не рендерится, аргумент вообще не привязан
к advice. Стережёт `AllureSpringAssertionsTest.nullAssertionsDoNotTouchValueToString`
(мутация-проверен). Урок общий: **`toString()` чужого объекта в имени шага — это побочный
эффект**, и смежный риск в JUnit-перехвате записан в `docs/review-log.md`.

⚠️ Остался известный шум: внутренняя проверка Spring теперь даёт шаг
«Проверка: exchangeResult unexpectedly null — значение не null» в каждом WebTestClient-тесте.
Зафиксирован в эталоне инвентаря, решение отложено.

⛔ **Нижняя граница Boot 3 сборкой больше не проверяется** — `compat-boot-min` не собирается
(зависимости Boot 4 не управляются BOM 3.2.12). См. `docs/compat-matrix.md`.

## Ручные правки фазы 2 — что оказалось на самом деле

⚠️ Ниже — план, писавшийся ДО фазы. Он не сбылся в одном: **в `src/main` править ПРИШЛОСЬ.**
`AllureRestTemplateInterceptor` приводил `HttpHeaders` к `Map<String, List<String>>`, а в
Spring 7 `HttpHeaders` перестал быть `MultiValueMap`. Правка — сменить тип параметра на
`HttpHeaders`: метод `forEach(BiConsumer)` объявлен и в 6.1, и в 6.2, и в 7.0 с одинаковой
сигнатурой (сверено по jar-ам), поэтому один jar по-прежнему работает на обоих мажорах.
Обещание «апгрейд не требует правок в src/main» касалось только кастомайзеров — и это
ровно тот случай, когда утверждение в документе шире, чем то, что его подтверждало.

**В остальном про кастомайзеры план оказался верен.** Оба автоконфига больше не привязаны к переехавшим типам на
этапе компиляции: интерфейс кастомайзера поднимается ПО ИМЕНИ из
`internal/MovedTypeNames` (`internal/MovedCustomizerRegistrar`), поэтому один и тот же jar
работает и на Boot 3.x, и на Boot 4.x. Появится ТРЕТЬЕ имя — дописать его в список, и это
единственное место.

Остальное — известные переезды, проверено по реальным BOM и jar-ам Boot 4.1.0:

- **`pom.xml`:**
  - `rest-assured` → **6.0.1** (пин уже есть; 5.5.6 собран на Groovy 4, а Boot 4.1 тянет
    groovy-bom 5 → транзитивный Groovy будет переуправлен). Внутренние классы, за которые
    держится наш перехват (`ValidatableResponseOptionsImpl`, `ResponseAwareMatcher`),
    в 6.0.1 на месте — проверено по jar;
  - `spring-boot-starter-aop` → **`spring-boot-starter-aspectj`** (артефакт переименован);
  - добавить `spring-boot-webmvc-test` и `spring-boot-webtestclient` (scope `provided`);
  - `spring-boot-test-autoconfigure` в 4.1 — почти пустой артефакт, нужных нам классов там
    больше нет; зависимость можно убрать.
- **Канарейку править НЕ нужно** — `InstrumentationApiCanaryTest` читает список имён из `internal/MovedTypeNames` и на Boot 4
  зеленеет по новому. Если её всё же пришлось править — значит появилось ТРЕТЬЕ имя, добавь
  его в список.
- **Surefire** поднять под JUnit Platform 6. Проверять `junit-platform.properties` руками больше
  не нужно: `unit/JUnitConfigurationTest` спрашивает у самой Платформы
  (`ExtensionContext.getConfigurationParameter`), вычитала ли она случайный порядок методов.
  Переедет механизм конфигурации — красный, а не тихо отключившаяся рандомизация.

## Порядок чтения сигналов

Сигналы срабатывают в этом порядке, и разбирать их надо так же — сверху вниз:

1. **Модель Maven / компиляция.** Падает первой, чинится механически (см. список выше).
2. **Канарейки** (`InstrumentationApiCanaryTest`) — «API чужой библиотеки уехал», точечно,
   с именем матчера и артефакта.
3. **`target/instrumentation-diagnostics/jvm-*.txt`** — `installed=false` (self-attach!) или
   ненулевые сбои трансформации. Проверяется автоматически, вторым прогоном.
4. **WARNING «[Allure Spring] модуль не активирован: …»** — фича у потребителя есть, крючка нет.
5. **Инвентарь** (`ReportInventoryCheck`) — «шаг исчез, а ошибок не было». Самый частый исход
   апгрейда: матчер просто перестал совпадать.

## Эталон инвентаря придётся обновлять — и это нормально

Заранее известные источники законных расхождений:

- **Hibernate 7.4** может изменить форму генерируемого SQL (кавычки и квалификация схемой в
  именах таблиц). Кавычки наш `tableName()` съедает, схему — нет: виды `SQL SELECT widget`
  могут стать `SQL SELECT public.widget`.
- **Liquibase 5** меняет служебный SQL (`DATABASECHANGELOG`/`LOCK`) — это отдельные виды.
- **Kafka 4.x** — KRaft-only, проверить `@EmbeddedKafka` в `KafkaTestApp`/`KafkaListenerTestApp`.
- **Кратность** поедет у СЛУЖЕБНЫХ видов: число запросов Liquibase к `DATABASECHANGELOG`
  и число SELECT от Hibernate решает чужая библиотека, а маркер там жёсткий (`×6`, `×5`, `×16`).
  Это ОЖИДАЕМОЕ расхождение, а не задвоение перехвата — сообщение гейта так и формулирует
  («либо перехват задвоился, либо витрина изменилась осознанно»). Пересев: `-Dinventory.counts=true`.
  Размен осознанный: требовать «наблюдения в двух кейсах» для жёсткого маркера нельзя — тогда
  почти всё стало бы `×≥1`, а это ЗАДВОЕНИЕ не ловит (проверено мутацией).

Правило прежнее: сначала глазами, потом `-Dinventory.update=true`. Удаление видов требует ещё и
`-Dinventory.remove=true` — красную сборку нельзя «чинить» сокращением сетки.

## Грабли байткода: временные загрузчики классов

Агент ставится ОДИН раз (при первом Spring-тест-классе) и обходит ВСЕ загруженные классы
(`RedefinitionStrategy.Reiterating`). Если к этому моменту в JVM висят классы из уже
**закрытого** загрузчика, ByteBuddy не может разрешить их описания —
`NoSuchTypeException: Cannot resolve type description for org.assertj.core.api.Assert` —
и трансформация этих типов срывается. Модули молча теряют шаги на ВЕСЬ прогон.

Замерено на нашем же сьюте: 20 прогонов со случайным порядком классов, ровно один красный —
тот единственный, где тест с временными загрузчиками отработал раньше первого Spring-теста
(30 упавших тестов в семи классах). Лечится порядком: инструментация ставится ДО появления
таких загрузчиков (`HiddenClassLoader.hiding` это гарантирует, стережёт
`unit/HiddenClassLoaderSafetyTest`).

⚠️ **У потребителя та же механика** — например, перезапускающий загрузчик Spring Boot DevTools
или изолированные загрузчики тест-фреймворков. Симптом тот же: тесты зелёные, шаги пропали,
в логе `NoSuchTypeException`. Гейт `InstrumentationFailures` такое видит и краснеет.

## Чего проверить нельзя было заранее

Форма SQL Hibernate 7.4 и служебного SQL Liquibase 5; работа RestAssured (Groovy) и
WireMock 3.13.2 на JDK 25; `@EmbeddedKafka` на Kafka 4.x; реальная бинарная совместимость
Allure с JUnit Platform 6. Всё это проверяется только запуском в соответствующей фазе.

## Хвосты, решение по которым принимается в ветке апгрейда

- `RestTemplate` объявлен deprecated в Spring Framework 7 (не удалён) — нужна политика по
  предупреждениям для `rest/AllureRestTemplate*`.
- `RestTestClient` (новый сервлетный клиент SF 7) — модуля под него нет. Это ОТДЕЛЬНАЯ фича
  после апгрейда, а не его часть.
- `sun.misc.Unsafe`: и на JDK 25, и на JDK 26 дефолт всё ещё `warn`, а не `deny` — проверено
  `java --help-extra` на установленном 26.0.1 (раньше здесь было написано «на 26 запрет» —
  неверно, строка генерировала ложную тревогу). Флаг `--sun-misc-unsafe-memory-access` в pom
  НЕ добавляем: поставить его «на всякий случай» значит спрятать сигнал. Разовый прогон с
  `=deny` полезен как диагностика — покажет, кто из зависимостей реально ходит в Unsafe.
- JDK 26 стоит локально — не соблазняться проверить «заодно»: это вторая переменная.
- Координата `allure-junit5` с 2.35 переименована в `allure-jupiter` (старая — pom-relocation).
  Переезд механический, но делать его лучше ОТДЕЛЬНЫМ коммитом до апгрейда: одна переменная за раз.
