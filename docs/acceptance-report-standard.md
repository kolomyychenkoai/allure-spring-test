# Стандарт приёмочного Allure-отчёта

Этот документ — критерий приёмки ПО ОТЧЁТУ (для архитектора / безопасника / тестера).
Рядом есть ещё три ревьюера со своими зонами: `java-lead` (код-крафт по
`docs/java-code-standard.md`), `maintainer` (декомпозиция/поддерживаемость + достаточность
тестов — отличает настоящие тесты от демонстраций) и `qa-lead` (стратегия качества над всем
сьютом + понятность и единообразие отчёта для МАСШТАБНОЙ ручной приёмки — отчёты принимают
~20 ручных QA: баланс уровней A/B, кросс-модульные риски, здоровье сьюта, процесс).
Приёмка идёт **по Allure-отчёту**, поэтому отчёт обязан быть самодостаточным:
по нему, **не открывая код тестов**, должно быть понятно — ЧТО проверялось, КАК
и почему результат верный.

Качество самого **кода** (идиомы Java, потокобезопасность, ресурсы, исключения, API,
javadoc) — отдельная зона: ревьюер `java-lead` по `docs/java-code-standard.md`. Этот
документ — про отчёт, тот — про код; они ссылаются друг на друга, а не дублируются.

## Главный принцип

> Если по шагам отчёта нельзя восстановить сценарий и убедиться в корректности —
> отчёт **не принят**, даже если все тесты зелёные.

## Эталонные модули (образец — не трогать без явной просьбы)

Пользователь зафиксировал (2026-06-23) модули, чей вид в отчёте его УСТРАИВАЕТ и которые
надо брать ЗА ОБРАЗЕЦ для новых/изменяемых модулей:

> **WireMock · Kafka · RestAssured · Логи+конфигурация · MockMvc · База данных (JPA)**

- Их формат шагов/вложений менять НЕ нужно без явной просьбы — равнять остальное на них.
- **Ассерты (AssertJ / Hamcrest / Spring-AssertionErrors) и Mockito** в эталон НЕ внесены —
  они не «залочены»: по ним можно предлагать улучшения (но имена шагов ассертов мы уже
  признали «на потолке» — см. историю; это не дефект).

## Обязательные требования к отчёту

1. **Осмысленные имена тестов.** `@DisplayName` — человеческим языком, по делу
   («Создание заказа сохраняет его в БД и шлёт событие в Kafka»), а не имя метода.

2. **Структура шагов Given/When/Then (или Arrange/Act/Assert).** Каждое значимое
   действие и проверка — отдельный `Allure.step` с конкретным названием:
   что делаем и с какими данными (`When: POST /api/orders {productName=laptop, qty=2}`),
   а не `step1`, `выполнить`, `проверка`.

3. **Каждый значимый эффект — вложение (attachment) с понятным именем:**
   - HTTP — запрос и ответ (метод, путь, статус, тело);
   - БД — выполненный запрос/состояние сущности;
   - Kafka — отправленное/полученное сообщение (topic, key, value);
   - конфигурация — срез настроек;
   - логи приложения за время теста.
   - **Тело JSON — ОТДЕЛЬНЫМ вложением** (`text/plain`-метаданные + тело вложением `«… Body»`/
     `«Значение сообщения»`), помеченным `application/json` и развёрнутым в столбик
     (`AllureAdviceSupport.attach` + `AllureJson.indent`) → Allure покажет с отступами и подсветкой.
     Не топить JSON-тело в общем text/plain-дампе метаданных.

4. **Успешные проверки видны как шаги; падения — НЕ фабрикуем.** УСПЕШНЫЙ ассерт даёт
   понятный шаг «значение X — оператор Y» (это МОДУЛЬ инструментирования AssertJ/Hamcrest/
   Spring делает сам, без `Allure.step` руками в тестах). УПАВШУЮ проверку шагом НЕ
   логируем: исключение пробрасывается, тест падает, и Allure из коробки кладёт
   сообщение+стек в результат теста. Никто не делает «красный шаг» для упавшего ассерта —
   достаточно понятного шага для НЕупавшего. Не дублировать текст исключения в
   шаг/вложение/`statusDetails` — это уже показал Allure на уровне теста (см. п.7).

5. **Входные данные — в параметрах теста** (Allure parameters), чтобы было видно,
   на каких данных гонялся сценарий.

6. **Группировка проставлена:** `@Epic` / `@Feature` (и `@Story`, где уместно) —
   чтобы отчёт читался по фичам, а не плоским списком.

7. **Диагностируемость падений — зона Allure, не наша.** Падение показывает Allure из
   коробки: тест помечается failed, сообщение+стек исключения — в результате теста. Мы
   НЕ реконструируем это шагами/вложениями. Локализацию даёт сочетание: УСПЕШНЫЕ шаги до
   точки падения (видно, что прошло) + падение теста от Allure (видно, что и почему сломалось).
   Идиома: не переизобретать то, что инструмент делает сам.

8. **Достоверность значений.** Показанное в шагах/вложениях обязано ПРАВДИВО
   отражать операцию: аргументы = то, что реально ОТПРАВИЛИ (а не мутированное
   состояние после вызова), результат = то, что вернулось. Значение, вводящее в
   заблуждение (классика: у `save` в аргументах виден сгенерированный БД `id`,
   которого на входе не было), — это ДЕФЕКТ, а не мелочь.

9. **Секреты (на текущем этапе).** Маскирование намеренно отключено — значения
   пишутся как есть, поэтому в тестах используем только фейковые/несекретные данные.
   Попавший в отчёт секрет — замечание информационное, не повод не принять.

## Чек-лист приёмки (быстрый)

- [ ] У каждого теста человекочитаемый `@DisplayName`.
- [ ] Видна структура Given/When/Then, шаги названы конкретно.
- [ ] Все внешние взаимодействия (HTTP/БД/Kafka/конфиг/логи) — во вложениях.
- [ ] УСПЕШНЫЕ проверки — шагами; упавшие НЕ фабрикуем (нет «красных» шагов/дублей
      текста исключения — падение показывает Allure на уровне теста).
- [ ] **Значения во вложениях достоверны** (прочитаны глазами, не по именам шагов):
      аргументы = отправленное, результат = вернувшееся, ничего не вводит в заблуждение.
- [ ] Проставлены Epic/Feature.
- [ ] В тестах только фейковые данные (маскирования секретов сейчас нет).
- [ ] По одному лишь отчёту можно провести приёмку сценария.

## Придирки ревью (уроки — проверять ОБЯЗАТЕЛЬНО)

Эти вещи ревьюеры пропускали, а пользователь ловил. Проверять всегда:

1. **Полнота перехвата.** Инструментирование должно ловить ВСЕ варианты технологии,
   а не только те, что демонстрирует тест. Сверять матчеры с РЕАЛЬНЫМ API библиотеки
   (`javap` по jar): все методы/перегрузки/делегации (все HTTP-методы и статусы; все
   типы SQL — INSERT/SELECT/UPDATE/DELETE/батчи; несколько запросов на один вызов; async).
   Что НЕ перехватываем by-design (reactive, ручная сборка, изолированные spec'и,
   параллельный запуск и т.п.) — должно быть ЯВНО задокументировано (README/javadoc),
   а не молча отсутствовать. «Счастливое подмножество» без оговорки — пробел.
2. **Не фабриковать падения.** Шаг — только для УСПЕШНОЙ операции/проверки. НЕ создавать
   FAILED/BROKEN-шаги для упавшей проверки и НЕ дублировать текст исключения в
   шаг/вложение/`statusDetails` — это уже делает Allure на уровне теста (см. п.4, п.7).
   Если ревьюер ПРОСИТ добавить «красный шаг»/`statusDetails` для падения — это ошибка
   направления. (Исключение: ошибка ОПЕРАЦИИ, где шаг структурно открыт до вызова, напр.
   репозиторий — там `BROKEN` — родная семантика Allure, но БЕЗ текста исключения.)
3. **Достоверность значений** (см. п.8) — читать ТЕЛА вложений, а не имена шагов.
4. **Читаемость и структура.** Шаги сгруппированы осмысленно (связанное — вложено,
   а не плоской чересполосицей); порядок логичный; по дереву видно «что породило что».
5. **Ноль кода в тесте.** В тестах НЕТ ручных `Allure.step`/ручной разметки ради
   красивого отчёта. Степы только от инструментирования. Хардкод = подделка, дефект.
6. **Вложения — под ассертом, не только шаги.** Проверять и НАЛИЧИЕ, и СОДЕРЖИМОЕ вложений
   (аргументы/результат/тело), на обоих уровнях. Перекос «ассертим имена шагов, а вложения
   нет» — пробел: регресс, теряющий/портящий вложение, проскочит.
7. **Полнота перехвата устойчива к ПОРЯДКУ ЗАГРУЗКИ классов.** Баг может быть невидим в
   полном прогоне (классы уже инструментированы прошлыми тестами), но проявляться в
   изолированном прогоне / у реального потребителя (класс загружен до агента → пропущен).
   Проверять полноту в РЕАЛЬНОМ Spring-контексте (уровень B), не только в плоском JVM.

## Соглашение об именах вложений

Чтобы отчёт читался единообразно по всем модулям:
- **сетевые протоколы** (HTTP) → `HTTP Request` / `HTTP Response`;
- **вызовы методов** (репозиторий, мок, и т.п.) → `<Префикс> Call` / `<Префикс> Result`
  (напр. `DB Call` / `DB Result`);
- **сырой запрос** (реальный SQL) → шаг `SQL <OP> <таблица>` (чтобы запросы
  различались в дереве), вложение `SQL Query`.
Префикс шага — короткий маркер технологии (`HTTP`, `DB`, `Kafka`, `Mock`…).
Новые модули должны следовать этому словарю, а не плодить третий вариант.

## Два уровня тестов: A (логика) и B (реальная цепочка)

- **Уровень A** (через `InMemoryAllure`) — детерминированно проверяет ЛОГИКУ
  инструментации, зовя её НАПРЯМУЮ. В файловом отчёте такие тесты пустые (пишут в память)
  — by-design. Но уровень A структурно НЕ ловит, что листенер зарегистрирован
  (`spring.factories`/`AutoConfiguration.imports`) и что байткод-матчер реально сработал.
- **Уровень B** (`*ReportIT`, `@SpringBootTest`) — гоняет РЕАЛЬНУЮ цепочку (регистрация +
  байткод/листенеры) и обязан АССЕРТИТЬ записанный отчёт, а не просто прогоняться. Механизм —
  `support/CurrentReport` (читает шаги/вложения текущего кейса, lifecycle не подменяя, поэтому
  шаги остаются в реальном отчёте — showcase сохранён). ⚠️ **Verify в `*ReportIT` — ТОЛЬКО через
  `CurrentReport.check(...)`/`assertStep(...)` (голый throw, немой на успехе). JUnit `assertTrue`/
  `assertEquals` в `*ReportIT` больше НЕЛЬЗЯ** — с перехватом JUnit Jupiter Assertions они сами
  становятся шагами «Проверка: …» и засоряют отчёт (+саморефлексивная рекурсия по `stepNames()`).
  Ни AssertJ, ни Hamcrest, ни Spring-ассерты в verify тоже нельзя (все инструментируются).
  Инвариант стережёт `ReportITVerifyChannelGuardTest` (source-scan, краснеет с именем файла).
  `assertThrows`-драйвер (заставить бросить) — можно, его шаг «брошено …» это законная витрина.
  Контент из
  `afterTestMethod` (логи, пошаговые WireMock-запросы) из тела теста не прочитать — он
  проверяется чтением записанного на диск результата (`anyResultFileContains`) из следующего
  упорядоченного теста.

`*ReportIT`, который ничего не проверяет в отчёте, — ДЕМОНСТРАЦИЯ, а не тест: пропустит
поломку регистрации/байткода/имени шага. Человекочитаемая приёмка по отчёту идёт по уровню B —
смотри именно его, и убедись, что он ассертит, а не только прогоняется.

## Уровень C: инвентарь отчёта (автоматический критерий приёмки)

Уровни A и B ловят поломку ТАМ, ГДЕ КТО-ТО ЗАРАНЕЕ НАПИСАЛ ПРОВЕРКУ. Инвентарь ловит везде:
он фиксирует ВСЕ виды шагов и вложений, которые сьют производит, и краснеет, если вид исчез.

- Эталон — `src/test/inventory/report-inventory.txt` (в гите, читается глазами, диффится в PR).
  Формат: `<ТестКласс> | <шаблон>  # <кто отвечает>`; `*` — вид без привязки к классу,
  `?` — необязательный вид.
- Проверка — `inventory/ReportInventoryCheck`, гоняется ВТОРЫМ прогоном surefire (execution
  `report-inventory`) в отдельной JVM: к этому моменту весь основной прогон на диске.
- Вид = пара «класс-владелец | шаблон». Одного имени шага мало: `HTTP GET … → 200` пишут пять
  модулей, и по имени не понять, кто отвалился.
- Нормализация (`inventory/StepTemplates`) маскирует ТОЛЬКО рантайм-мусор (порты, мс, хэши,
  сгенерённые id, счётчики, сравниваемые значения). Операторы ассертов, SQL-операции и таблицы,
  HTTP-методы/пути/статусы, топики — СОХРАНЯЮТСЯ: по ним видно, что модуль жив.
- Тип вложения (mime) и признак непустоты — часть вида: деградации «сломался притти-JSON»
  (`application/json → text/plain`) и «вложение пишется, но пустое» иначе прошли бы молча.
- Вложенность — часть вида (`DB Repo.save ▸ SQL INSERT widget`): регрессия «SQL перестал
  вкладываться и вылез на верхний уровень» даёт тот же набор ИМЁН, и без этого была бы невидима.

**Границы сетки (что инвентарь НЕ ловит).** Честно, чтобы «уровень C» не читался как «ловит всё»:
кратность (10 SQL-шагов и 1 SQL-шаг — один вид, так задумано: количества плавают);
порядок шагов-братьев на одном уровне (вложенность стережётся, чересполосица — нет);
статус шага (passed → broken при том же имени); метки `epic`/`feature`, параметры и
`@DisplayName`; содержимое вложений глубже признака «пусто/непусто».

**Главная граница — структурная: инвентарь стережёт только то, что ДЕМОНСТРИРУЕТ витрина.**
Вида, которого нет в демо-`*IT`, нет и в эталоне, — значит новый непокрытый вариант перехвата
отвалится молча. Придирку №1 («полнота перехвата — ловим ВСЕ варианты технологии, а не только
показанные») уровень C не закрывает by design. Лечится не детектором, а дисциплиной:
**новый вариант перехвата → строка в витрине**, иначе он вне сетки.

**Инфра-тесты в отчёте.** Канарейки, тесты активации и инвентаря помечены
`@Epic("Внутренние проверки библиотеки")` и используют НЕМОЙ канал (голый `throw`), а не
JUnit-ассерты: перехваченный `assertTrue` сам стал бы шагом «Проверка: …» и засыпал бы
витрину девелоперским жаргоном (до этой правки одна канарейка давала 112 шагов —
больше, чем вся демо-витрина).

**Изменил отчёт осознанно** (добавил шаг, переименовал вложение) — обнови эталон:

```bash
mvn clean test -Dinventory.update=true   # перезапишет файл и НАМЕРЕННО упадёт
git diff src/test/inventory/report-inventory.txt   # проверить глазами и закоммитить
```

Падение при обновлении — не баг: так флаг невозможно оставить включённым в автопрогоне,
а обновление эталона остаётся человеческим решением.

Три сигнала об апгрейде библиотек не перекрываются, держать все три:
канарейка (`InstrumentationApiCanaryTest`) — «API уехал»; `InstrumentationDiagnostics` —
«перехват упал с ошибкой»; инвентарь — «шаг исчез, ошибок не было» (типичный случай при
апгрейде: матчер просто перестал совпадать).

## Как получить отчёт

```bash
cd ~/projects/allure-spring-test
mvn test                 # генерирует target/allure-results
mvn allure:report        # статический отчёт -> target/site/allure-maven-plugin
mvn allure:serve         # открыть в браузере
```

Для машинной проверки содержимого — читать JSON из `target/allure-results/`
(`*-result.json`: поля `name`, `steps`, `attachments`, `parameters`, `status`;
тексты вложений — в соседних `*-attachment.*`).
