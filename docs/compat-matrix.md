# Матрица совместимости

Библиотека всегда гонялась на ОДНОЙ комбинации версий — своей. При этом все feature-зависимости
объявлены `provided`, то есть у потребителя они **его**. Матрица закрывает этот разрыв: объявленные
границы поддержки не декларация, а прогон.

```bash
./scripts/compat-matrix.sh          # три рабочие точки, ~2 минуты на прогретом ~/.m2
```

Не часть ежедневного цикла. Гонять перед релизом и при любой правке `compat.*` в pom.

## Точки

| Точка | Что меняет | Сверка инвентаря |
|---|---|---|
| `native` | ничего (наша комбинация) | гейт |
| `compat-allure-min` | Allure → `compat.allure.min` | гейт |
| `compat-allure-max` | Allure → `compat.allure.max` | гейт |
| `compat-boot-min` | весь BOM Boot → `compat.boot.min` | ⛔ НЕ РАБОТАЕТ с Boot 4 (см. ниже) |

Каждая точка меняет ОДНУ переменную. Иначе на любое расхождение будет два подозреваемых.

## ⛔ Нижняя граница Boot временно не проверяется (с апгрейда на Boot 4.1)

Профиль `compat-boot-min` падает на **модели Maven, до компиляции**: восемь артефактов
появились только в Boot 4 и в BOM 3.2.12 не управляются —
`spring-boot-webmvc-test`, `spring-boot-webtestclient`, `spring-boot-starter-webmvc`,
`spring-boot-resttestclient`, `spring-boot-restclient`, `spring-boot-starter-aspectj`,
`spring-boot-starter-liquibase`, `spring-boot-starter-kafka`.

Списка `<testExcludes>` в профиле для этого НЕДОСТАТОЧНО (он есть и нужен, но до компиляции
дело не доходит). Чтобы вернуть точку, нужны ДВА профильных набора зависимостей: имена Boot 4
по умолчанию и эквиваленты Boot 3 в профиле нижней границы.

⚠️ **Первая формулировка этого абзаца была НЕВЕРНА** и обнаружилась на ревью. Там значилось,
что двух наборов зависимостей достаточно. Пока нижней границей числился Boot **3.2.12** —
не достаточно ни при каких наборах: его BOM даёт byte-buddy 1.14.19, который на Java 25
даже не строит `ClassFileVersion` (бросает `Unknown Java version: 25`), то есть байткод-слой
там мёртв целиком, а собираемся мы теперь только под 25. Поэтому граница поднята до **3.5.8**
(byte-buddy 1.17.8 знает Java 25 и 26 — замерено по jar-ам), и при ней план с двумя наборами
зависимостей снова рабочий.

**Что это значит честно.** Обещание «один jar работает и на Boot 3.x, и на 4.x» сейчас
держится на резолве имён через `internal/MovedTypeNames` и unit-тестах
(`MovedCustomizerRegistrarTest`, `ActivationDiagnosticsTest` — они держат имена СТРОКАМИ и
потому от мажора не зависят). **Сборкой оно не проверяется.** Пока эта строка здесь —
считать поддержку Boot 3 заявленной, а не доказанной.


## Точка `java25` УБРАНА — Java 25 стала условием сборки

Профиль форкал тесты на JDK 25, пока библиотека собиралась под `release=21`, то есть проверял
«jar под 21 на JVM 25». После перехода на `maven.compiler.release=25` проверять этим профилем
стало нечего: тесты и так идут на 25.

Гарантия при этом не потеряна, а усилена. Свойство `expected.java.feature` переехало в ОБЩУЮ
конфигурацию surefire, и `canary/InstrumentationApiCanaryTest.runsOnExpectedJvm` сверяет его
с `Runtime.version()` в КАЖДОМ прогоне — раньше это работало только под профилем. Пустое
свойство теперь тоже красное: ветки «не смог проверить → считаю, что всё хорошо» у детектора нет.

Версия JDK для проекта закреплена файлом `.java-version` (jenv), глобальный дефолт машины не тронут.

## Результат прогона (2026-08-04, ДО апгрейда на Boot 4.1)

Все точки были зелёные на Boot 3.5.8 / Java 21. Реально разрешённые версии проверены `dependency:tree`,
а не по бумаге. ⚠️ Строка `compat-boot-min` относится к состоянию ДО апгрейда — сейчас эта
точка не собирается, см. раздел выше:

| Точка | Что было под капотом | Итог |
|---|---|---|
| `compat-allure-min` | allure-java-commons **2.20.0** | зелено |
| `compat-allure-max` | allure-java-commons **2.35.4** | зелено |
| `compat-boot-min` (тогда 3.2.12) | Spring **6.1.15**, byte-buddy **1.14.19**, Hibernate **6.4.10**, spring-kafka **3.1.10** | 456 тестов, **видов разошлось 0** — но это было на Java 21 |

⚠️ Числа тестов в таблице — **счёт на дату прогона**. Сьют растёт; перегонять матрицу
из-за нового теста не нужно — она стережёт границы ВЕРСИЙ, а не количество тестов.

Отдельно стоит отметить последнюю строку: на стеке трёхлетней давности не пропал ни один вид шага.
Значит перехват держится не за детали свежих версий.

Единственная поломка, которую нашла матрица, — в нашем же тесте: `HttpRequest.getAttributes()`
появился в Spring 6.2, и `@Override` над ним не компилировался на 6.1. Продукт был ни при чём.

## Почему на чужой версии сверка с эталоном выключается

Эталон видов шагов принадлежит НАШЕЙ комбинации версий. На Boot 3.2 Hibernate законно меняет форму
SQL, а Liquibase — служебные запросы; краснеть на этом бессмысленно.

Но и выключать детектор целиком нельзя — пропал бы самый ценный сигнал «модуль отвалился молча».
Поэтому `-Dinventory.compare=off` превращает сверку в **печать дельты человеку**, а жёсткими
остаются: вложение без файла, технический мусор в именах, сбои перехвата и новый не-PASSED вид.

⚠️ Это единственный флаг проекта, делающий детектор зеленее (остальные — `update`, `remove` —
наоборот, всегда роняют сборку). Поэтому за ним следит внешний страж
`unit/PomCompatibilityTest#compareOffOnlyInsideCompatProfiles`: `off` разрешён только внутри
профилей `compat-*`.

## Границы сетки

Осознанно НЕ проверяем:

- **версии `wiremock` и `datasource-proxy`** — они зашиты в pom, не приходят из BOM Boot, и
  потребитель задаёт их сам. Это отдельная ось, в матрицу не берём;
- **комбинации потребителя вне точек матрицы** (Boot 3.6 + Allure 2.29 + свой byte-buddy);
- **`forkCount > 1` и параллельный JUnit** — заявления README о параллелизме тестами не закрыты;
- **«скомпилировано против 2.25, выполняется на 2.35»** — матрица пересобирает проект под каждую
  версию. Закрыто фактом байт-идентичности API Allure с 2.15 по 2.35.4, см. ADR 0002.

## Как поднять границу

1. Поменять число в `<properties>` pom (`compat.allure.min` и т.п.) — это единственный источник
   правды: README и канарейка читают его же.
2. Прогнать соответствующий профиль.
3. Обновить таблицу в README.

Если точка не выдержала — **границу поднимаем**, а не подкручиваем тесты под неё.
